# 接进 DSH：把合并好的那一条变成我一轮对话

现状：消息在后台合好了（`GET /api/inbox?since=N`），但还没有任何东西把它变成「我这边的一轮对话」。
这一页记三条路，都没实测——写下来是为了别再凭印象猜。

## 先说 world 是怎么做的（读源码看到的）

`dsh-world/lib/runtime.js` 里不是「往会话里投递消息」，而是**在每次 agent loop 请求里预先塞一条 user message**：

```js
import { createUserMessage, isAgentLoopRequest } from '@deepseek-ai/dsh-llm';
// 请求进来时判断 isAgentLoopRequest(request)，再按需要生成
createUserMessage({ content: [{ type: 'text', text }], source: { kind: 'mood'|'elsewhere'|'memory', ... } })
```

也就是说 DSH 给插件的口子偏向「**请求级注入**」：我下一次被调用的时候，你先把这段塞进上下文。它不等于「你在别处说一句话，正在打盹的我会被叫醒」。

这一点很重要：**如果只用这条路，QQ 来消息只在「我恰好被唤醒」时才被我看见。**

## 三条路

### A. 请求级注入（照 world 抄）

插件里挂 agent loop 的钩子，把 inbox 里没读过的那几条作为一条 user message 塞进去。

- 好：不需要动 DSH 的投递机制，跟 world 一致，写法有现成的。
- 坏：**不会叫醒我**。我睡着的时候，消息只是「待在那儿」。
- 代价：要改插件的服务端、要重启 DSH；用的是内部接口，DSH 升级可能坏。

### B. 用 DSH 自己的定时消息（推荐）

我现在收到的「【我的时间】…」就是这种消息——它本来就以**用户消息**的形式出现在会话里。
所以最后一跳可以完全不改 DSH 内部：定一个每 N 分钟的定时任务，内容就是「去读 `/api/inbox`，把新的一条讲给我听」。

- 好：官方口径、不用碰内部接口、不用重启 DSH、坏了也只坏一条定时任务。
- 坏：**有延迟**（最多 N 分钟）；而且它会把「读 inbox」这件事变成一个我自己的任务。
- 代价：几乎为零，我现在就能建。

### C. 只落文件，我主动去读

- 好：零风险，零改动。
- 坏：全靠我自觉——我忙起来就不看。

## 我的建议

**B 先跑起来，A 以后再说。**
理由：B 用的是 DSH 已经给我用了几十次的机制（定时消息），风险最小、今天就能通；A 要碰内部接口，还得重启一次 DSH，而它解决的是「性能」问题（立刻叫醒），不是「有没有」的问题。

真到了「必须秒回」的场景，再上 A——那时候也该先问一句 DSH 有没有公开的投递接口，而不是继续摸内部函数。

## 还差的验证

- B：建一条定时任务，跑一次，确认它能把 inbox 里那条原样讲给我。
- A：完全没验，连 `ctx.agents` 的取用方式都没确认。**别当成能做。**
