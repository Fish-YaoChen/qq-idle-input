# 已知问题

这些都是开发时真踩到的，不是猜的。每条都写清「现象 / 原因 / 现在怎么处理」。

## 一、读到只有十来个元素，像「界面空白」

**现象**：自检或读会话时，元素数只有 11 个、文本节点 0 个。看起来像「QQ 没加载完」或「改版了」。

**原因**：QQ 一个进程里有**五个** `Chrome_WidgetWin_1`——主窗、悬浮窗两个、还有**两个 32×39 的托盘小窗**。
按 `ProcessId` 找第一个窗口，抓到的是那个 32×39 的。

**处理**：改成**按窗口面积挑最大的那个**。三位脚本（selfcheck / qq-read / qq-send）都用这条规则。
实测：就算把 QQ 关进托盘，主窗也能读到 273 个元素、九行会话。

## 二、把 QQ 窗口卡死（能拖、点不动）

**现象**：窗口能拖动，点任何地方没反应；进程活着、`WM_NULL` 也应答，所以「进程是否响应」这个指标查不出来。只能重启实例。

**原因**：对**已经藏进托盘的窗口**做 `Invoke`（打开会话）或 `SetFocus`。渲染层卡在中间状态。
开发时踩了两次，两次都是这一步。

**处理**：**窗口不可见时不做任何交互**。先 `ShowWindow(SW_SHOWNOACTIVATE)` 显示出来（不抢焦点），显示不出来就直接拒。规矩写在 `qq-read.ps1` 的 `Ensure-Visible` 和 `qq-send.ps1` 里。

**恢复办法**：结束这个 QQ 实例，用带参数的命令行重新启动，再重新注入（如果你也在用它做桥）。

## 三、发消息会抢前台，全屏程序被最小化且还原不回来

**现象**：发送时前台被占 1.8–2.4 秒；如果当时在全屏游戏里，游戏被最小化，之后 `ShowWindow(SW_RESTORE)` 和 `SetForegroundWindow` 都返回成功，但 `IsIconic` 一直是 True——只有手动点任务栏才回来。

**原因**：写文字必须走真实键盘（输入框是 ProseMirror，UIA 只给只读的 Text；Chromium 不认外部 PostMessage 的 `WM_CHAR`）。真实键盘要求窗口在前台。全屏独占程序不吃标准还原。

**处理**：接受它，并把代价写在界面上。发送前先看空闲时间（`GetLastInputInfo`），手在动就不发。

## 四、UIA 的 `IsOffscreen` 不可靠

**现象**：窗口已经关进托盘，`IsOffscreen` 还是 `False`。

**处理**：用 `IsWindowVisible` 判断可见性，别用 `IsOffscreen`。

## 五、回车发不出去、粘贴也进不去

**现象**：`SendInput` 发 Enter 键，QQ 不发送；`Ctrl+V` 粘贴，输入框还是空的。但逐字 `SendInput`（`KEYEVENTF_UNICODE`）能打进去。

**处理**：文字用逐字发送；**发送改成 `Invoke` 那个「发送」按钮**（类名 `send-msg`），不需要键盘。

**教训**：发完必须**回读输入框**，空了才算发出去。开发时先只验了「字进了输入框」就报成功，结果那条是草稿。

## 六、发错会话

**现象**：把消息发进了上一个开着的聊天。

**原因**：按名字找元素，找到的是消息里的头像名，不是会话行；`Invoke` 到它身上不会切会话，字就打进了当前聊天。

**处理**：
1. 只认「会话行」——一个 Group，直接子节点里 2–3 个 Text，第一个是昵称；
2. 打开后核对聊天窗口顶部 `chat-header__contact-name`，不等于目标就**一个字不打**；
3. 发送前再核对一次。

## 七、改了 QQ 备注，白名单对不上

**现象**：白名单里写着「妈妈」，用户把备注改成「辰」，那一项就失效了——它会静默变成「关」。

**原因**：无障碍树里只有显示名（备注优先，其次昵称），**没有 QQ 号**，所以没法用稳定的键。

**处理**：面板在「白名单里有名字这次没找到」时给提示，并给「迁移到（选一个新会话）／删掉」两个按钮，改名之后两下接上。这是「改得快」，不是「不改」——根治要等能读到 uin 的那天。

## 八、白名单按名字记，重名会串

**现象**：两个会话显示同一个名字时，白名单分不清是哪个。

**处理**：面板标 `⚠重名` 并提示去 QQ 里改备注区分。**没有自动消歧**，因为树里没有别的标识可用。

## 九、中文字段在 node 里变乱码

**现象**：PowerShell 脚本输出中文键的 JSON，node 端解析出来键名乱码（JSON 能解析，但取不到字段）。

**原因**：控制台输出编码不是 UTF-8。

**处理**：调 PowerShell 时先 `[Console]::OutputEncoding=[System.Text.Encoding]::UTF8`，并把 `execFile` 的 `encoding` 设成 `utf8`。
另外**参数里的开关（`-Json`）不能加引号**——加了 PowerShell 会当成普通字符串，参数绑定不上。

## 十、`.ps1` 必须带 BOM

写完的脚本如果没 BOM，Windows PowerShell 会按 GBK 读，中文全烂、报 `Missing '=' operator` 这种莫名其妙的错。
**每个 .ps1 保存后确认前三个字节是 `EF BB BF`。**

## 十一、插件里 `spawn(process.execPath)` 拿到的不是 node

**现象**：面板服务起来之后，进程命令行是 `"E:\DSH NEXT\DSH NEXT.exe" server.mjs`，不是 `node server.mjs`。

**原因**：在 Electron 里 `process.execPath` 是宿主程序（DSH NEXT.exe），不是 node。脚本照样能跑（Electron 直接执行 JS），但这意味着：换了宿主、或者宿主加了限制，行为就不一样。

**处理**：暂时接受。更稳的做法是找 DSH 提供的 node 路径，或者把面板服务改成 DSH 插件内部的一个模块（不另起进程）。等真出问题再说——现在它能跑。

**另**：这也解释了「装进 `node_modules` 之后配置会被覆盖」那件事——面板的 cwd 在包里，所以配置得挪到 `~/.dsh/qq-idle/`。

## 十二、窗口白了，树还是好的

**现象**：QQ 窗口一片白，点不动；可自检和 `qq-read` 照样读得到会话、消息（实测 290 个元素、58 个文本节点）。

**原因**：渲染层不画了。长时间缩在托盘/最小化之后，Chromium 把合成器停了或者图面丢了。**不是页面坏了，也不是 QQ 改版。**（跟前面「元素只剩 10 个」不是一回事——那个是抓错了窗口。）

**处理**：`core/qq-repaint.ps1`。还原窗口（`SW_SHOWNOACTIVATE`，不抢焦点）→ 尺寸抖一像素（`SetWindowPos` 只改尺寸，不挪位、不改层级）→ 再看文本节点数。11-21 凌晨实测一次就恢复，**没重启 QQ、桥没断**。

**别急着重启。** 先跑这个：重启会掉注入，还得重新注一遍。

## 十三、最小化的时候 `GetWindowRect` 只有 160×28

**现象**：自检报「读不可以、一行会话都没认出来」，但人眼看 QQ 好好的，只是缩在任务栏。

**原因**：窗口缩小时 `GetWindowRect` 回的是缩略位置。主窗量出来 160×28=4480，旁边那张「资料卡」浮窗是 390×475=185250——**按面积挑窗口就挑到资料卡上了**，在浮窗里找会话，当然 0 行。

**处理**：两处一起改。
- `selfcheck.ps1`：主窗改按**无障碍元素数**挑（主窗几百个、浮窗几十个、托盘小窗十来个），元素数一样再比面积。
- `qq-read.ps1` / `qq-send.ps1`：新增 `AreaOf()`，窗口最小化时改用 `GetWindowPlacement` 的「还原后」尺寸来比。

**面积只在窗口正常时不骗人。**

## 十四、屏幕上一块点不动：QQ 的浮窗置顶了还看不见

**现象**：屏幕某一块（实测 (872,276)–(1252,743)）鼠标能移过去，但点不动；截屏软件能框出那块；底下内容看着正常。

**原因**：那底下压着一张 QQ 的「资料卡」浮窗（`hwnd=592682`，`Chrome_WidgetWin_1`，标题「资料卡」，矩形 (872,276)–(1262,751)）。它的 `WS_EX` 里有 **`TOPMOST` + `TOOLWINDOW` + `LAYERED`**——置顶、且是工具窗、还是半透明的，于是**看不见却把鼠标事件全吃了**。

**怎么查**：`WindowFromPoint(那块的中心)` 一眼就能看见是谁。光看截图看不出来，因为它本来就看不见。

**处理**：`core/qq-popups.ps1`。
- `.\qq-popups.ps1` 列出 QQ 进程里「置顶 + 工具窗 + 有面积 + 标题不是 QQ」的窗口；
- `.\qq-popups.ps1 -Fix` 用 `PostMessage(WM_CLOSE)` 关掉，关不掉就 `SW_HIDE`。

**只用消息，不碰键鼠**，所以不会像 `Invoke`/`SetFocus` 那样把渲染层弄拧。

**它跟「窗口白了」是连着的**：渲染层卡住的那一晚，主窗白了、这张卡留在最上层没跟着消失。修白屏（十二）之后它还在，得单独关。

## 十五、「必须带 --force-renderer-accessibility」这句是错的

**现象**：11-20 记的是「没这个参数，读到的界面树是空的」。11-21 早上实测：两个号都没带参数，照读。

| 状态 | 元素 | 文本节点 |
|---|---|---|
| 2727950855 主窗，vis=False（藏着，之前显示过） | 115 | 28 |
| 2653935317 主窗，vis=False | 295 | 147 |
| 同号小窗 / 托盘窗 | 9–10 | 0–1 |

`qq-read -Sessions` 不带参数，九行会话全读出来了。

**推断**：Chromium 的无障碍树在窗口**渲染过一次之后会留着**，藏起来也在。参数的作用是「一开始就把树建好，不用先让窗口显示一次」。11-20 那个「0 个节点」是**白屏、从没渲染过**的产物，不是缺参数。

**处理**：自检把这一项从 ❌ 降成 ⚠️（「没带这个参数」不再是硬失败），读到底行不行看「无障碍树有内容」那项的实际数字。文档、`qq-read` 的警告文案一起改。

**还没验的**：全新启动、从没显示过的窗口，不带参数到底能不能读。这条留着，别当成已知。

## 十六、两个号同时登着，自检和读会各挑各的

**现象**：11-21 早上自检验的是 2653935317（椰子），`qq-read` 读的是 2727950855（小肥鱼），两边元素数和会话数对不上，我差点判成「树坏了」。

**原因**：三个脚本各有一套挑进程的规矩。自检没指定号时优先挑带参数的实例，没有就取第一个 `background.js`；`qq-read` 的 `-Uin` 默认写死成 2727950855。规矩不一样，结果就不一样，而且**谁都没说自己验的是哪个号**。

**处理**：自检现在把「登录号」打在结果里；同时登着多个号时给⚠️，明说「这次只验了 X，要验另一个用 -Uin」。

**教训**：进程/窗口这种东西，「挑一个」本身就是个决定。挑完必须报出挑的是谁，不报就是隐患。
